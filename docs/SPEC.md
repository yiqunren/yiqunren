## 1. 產品目標

讓一個人在自己的電腦上，用一個網頁介面同時指揮多家 AI（例如 OpenAI Codex、Anthropic Claude Code、xAI Grok 的 CLI 或 API），讓它們各自回答、一起討論、互相審查，最後把成果落在使用者自己的專案上。

核心價值：

1. **多家並列**：同一個問題可以同時問多家，比較不同觀點。
2. **互相制衡**：一家做、另一家審，降低單一模型的盲點。
3. **人做最後決定**：AI 的產出一律是候選，要由人確認才算數。
4. **出錯時不亂猜**：狀態不明時明確標示「未知」，交給人核對，不自動重試、不假裝成功。

## 2. 名詞

- **成員**：一個可被指派工作的 AI，背後接某家的 CLI 或 API。
- **轉接器**：把某家 CLI 或 API 包裝成統一介面的元件。每家一個。
- **回合**：送給某個成員一次請求，到拿回一次結果（或失敗、中斷、未知）。
- **工作區**：成員被允許寫入檔案的資料夾。
- **主持人**：群聊裡負責框定問題與整理結論的成員。
- **擁有者**：使用這套系統的人。系統預設只有一位擁有者。

## 4. 功能需求

### FR-1 成員設定

- 擁有者可以新增、停用、刪除成員；每個成員指定一個轉接器、顯示名稱、模型與推理強度（若該家支援）。
  - 轉接器在新增時決定，之後不能改；要換轉接器就新增另一位成員。
  - 停用：設定保留，不能再送新回合，可以再啟用；已經在跑的回合不受影響。
  - 刪除：成員設定拿掉，過去的對話照樣保留，回合上記著當時的成員顯示名稱；還有進行中回合的成員不能刪。對話要刪由擁有者另外刪（FR-2）。
- 模型清單由轉接器提供；設定的模型不存在時拒絕啟動該成員，不自動換成別的模型。
  - 分期：轉接器能提供模型清單之前，模型先存成擁有者填的文字（空白表示用該家預設），不比對清單；轉接器提供清單後，送出回合前檢查，不存在就拒絕。
- 憑證（API key、CLI 登入）由擁有者自己在本機設定。系統不提供、不內建任何人的憑證。
- 每個轉接器都支援兩種認證模式，由擁有者逐一成員選擇：
  - **API key 模式（基準）**：使用擁有者自己的 API key，費用由擁有者向該家支付。三家官方都認可這種用法。
  - **訂閱 CLI 模式（省錢選項）**：呼叫擁有者自己安裝、自己登入、未經修改的官方 CLI。系統不讀取、不儲存、不經手該 CLI 的登入憑證或 token，也不代替擁有者登入。某家條款不允許時，該家不提供這個模式。
- 選擇訂閱 CLI 模式時，介面要提示：使用時須遵守該家的服務條款，由擁有者自行負責。
- 系統不代付、不轉售任何一家的 AI 用量。
- 每個成員可以設定單回合逾時（預設 15 分鐘，範圍 1～60 分鐘）。
- 介面顯示每個成員目前的狀態：閒置、執行中、需要人核對。
  - 有進行中回合是「執行中」；否則最近一個回合是「未知」時是「需要人核對」；其他是「閒置」。擁有者送出新回合後依新回合重新判斷；另外的「已核對」確認動作留給 FR-10。
- 私聊送出回合時選的成員必須存在而且沒有停用；回合使用該成員的轉接器、模型、推理強度、認證模式與單回合逾時。

### FR-2 私聊

- 擁有者選一個成員，送出訊息，收到回覆；同一段對話可以續問，成員保有前文脈絡（由轉接器負責續接該家的對話）。
- 同一段對話同時只能有一個進行中的回合；上一個回合還沒結束，不接受新訊息。
- 回合進行中，介面顯示「執行中」與經過時間；可以按「中斷」。
- 回合的結束狀態只有四種：**完成**、**失敗**、**已中斷**、**未知**。
  - 完成：存下回覆。
  - 失敗：顯示固定分類的錯誤原因（例如額度不足、認證失敗、逾時），不顯示原始錯誤全文。
  - 已中斷：確認成員的程序已經停止後才標示。
  - 未知：無法確認結果或程序是否停止時使用，並提示擁有者核對。
- 失敗或未知都不自動重試，由擁有者決定要不要重送。
- 網頁重新整理或伺服器重啟後，進行中的回合要能查回狀態；查不回時標為未知，不當作失敗也不當作成功。
- 回覆長度有上限（預設 100 KB，指回覆以 UTF-8 編碼後 100,000 位元組），超過時明確告知，不默默截斷：回合標為**失敗**，錯誤原因是固定分類「回覆過長」，回覆不存，也不存截斷後的內容。
- 擁有者送出的訊息與成員的回覆都存在本機狀態資料庫；網頁重新整理或伺服器重啟後，看得到這段對話的完整內容。
- 對話保留到擁有者刪除為止，不自動過期。擁有者可以刪除一整段對話，刪除時訊息、回覆與回合紀錄一併刪掉；還有進行中回合的對話不能刪除。

### FR-3 群聊討論

- 擁有者提出一個議題，選擇參與的成員（至少兩位）與一位主持人。
- 流程：
  1. 主持人先確認議題是否清楚；不清楚就回問擁有者，整場暫停。
  2. **第一輪**：每位成員收到完全相同的輸入，各自獨立回答，彼此看不到對方的答案。
  3. **第二輪**：每位成員閱讀第一輪全部答案與主持人的追問，提出補充、反駁或修正。
  4. 主持人整理結論：共識、分歧、未解問題與建議下一步。
- 整場的發言次數有上限，預設為 2N+3 次（N 是本場參與成員數，不含主持人）。這個數字對應上面的流程：主持人開場、第一輪每位成員各一次、主持人追問、第二輪每位成員各一次、主持人結論。三位成員時是 9 次。到上限就由主持人收尾。
- 群聊中的成員只交換文字，不使用工具、不讀寫檔案、不上網。
- 某位成員失敗或額度不足時，跳過該成員、標示缺席原因，其他人繼續；主持人失敗則整場結束並保留已有內容。
- 開場時檢查各家額度（若轉接器能查）：低於門檻（預設剩餘 10%）的成員本場跳過；額度查不到時視為未知，不跳過。
- 擁有者可以隨時停止整場；已經在執行的發言跑完或確認停止後才算結束。
- 第一輪全部完成前，不公開任何一家的答案，避免後續被先看到的答案影響。
- 議題、各成員與主持人的發言，依 FR-2 相同的規則保存與刪除。

### FR-4 決策模式（v0.2）

群聊的另一種模式，用來做選擇題式的決定：

1. 主持人把問題整理成 2～4 個選項與 1～4 條判斷標準，自己不表態。
2. 每位成員各自選擇一個選項（或都不選），附理由、信心、成立條件、風險與未證實的假設。
3. 指定一位成員擔任紅隊，專門找多數意見的弱點。
4. 主持人依標準整理結果，明確寫出建議選項、主要反對理由與哪些條件改變時應該重新考慮。

成員的輸出要符合固定格式；格式不符時該成員標為無效，不猜測其意思。

### FR-5 派工（v0.2）

- 擁有者用一句話描述要做的事；由一位「調度」成員把它整理成工作卡：目標、交付內容、允許修改的範圍、限制、1～3 條完成條件、建議的執行成員。
- 工作卡只是提案。擁有者確認（可先編輯）後才開始執行。
- 執行成員只能在自己的工作區內寫入。
- 執行結束後，工作卡進入「待驗收」，由擁有者逐條完成條件標記達成、未達成或未知，並寫下證據或原因。
- 執行失敗或中斷時，工作卡標為「未完成、結果待核對」，不自動重試、不換人。

### FR-6 專案綁定與唯讀檢視（v0.2）

- 擁有者可以登記自己的專案資料夾，並設定排除清單（例如 `.env`、憑證、個人資料）。
- 被綁定到專案的群聊或私聊，成員可以讀取專案內容，但只能透過唯讀檢視；排除清單內的檔案對成員不可見。
- 唯讀檢視必須由作業系統層級的隔離保證（例如唯讀掛載或沙箱），不能只靠提示詞要求。

### FR-7 實作加審查（之後）

- 從工作卡出發：一位成員在專案的隔離副本裡實作並跑測試，另一家的成員審查改動。
- 改動不直接套用到原專案；擁有者看過差異、測試與審查結果後，自己決定是否採用。
- 系統不自動 commit、push 或部署。

### FR-8 顧問角色（之後）

- 預先定義的專業角色（例如專案管理、資訊安全、法律、行銷），每個角色有使命、需要的輸入、檢查方法、證據要求與輸出格式。
- 用途是對已完成的成果做第二角度的複核；顧問提出的是待核對的建議，不是結論。
- 顧問不使用工具、不寫檔。

### FR-9 無人值守排程（之後）

- 擁有者設定任務清單與時間窗（例如凌晨 1～6 點），系統在窗內一次挑一項執行，只做唯讀審查。
- 排程只能用 API key 模式的成員；訂閱 CLI 模式的成員不能排進無人值守排程。
- 每份報告由另一家成員複核後才進收件匣；沒經過複核的要標明。
- 必須有兩層費用上限：單項上限與每晚總上限；到總上限就停止當晚其餘工作。
- 擁有者正在使用系統、或有工作區正在寫入時，排程讓路，不搶資源。

### FR-10 待處理收件匣（v0.2）

- 集中顯示需要擁有者處理的事：待驗收的工作卡、狀態未知的回合、排程報告、系統異常。
- 每一項先用一行說明「要不要處理、為什麼」，細節收合，點開才看。

### FR-11 視覺化辦公室（之後，可選）

- 用 2D 場景呈現成員與他們的狀態（閒置、執行中、需要核對）。
- 美術素材只能用本專案自製的，或授權允許商用與再散布的素材（例如 CC0），來源記進 `THIRD_PARTY_NOTICES.md`。

## 5. 跨功能需求

### NFR-1 執行狀態與冪等

- 每個請求帶一個由前端產生的唯一 ID。相同 ID、相同內容重送時，回傳原本的結果，不重複執行；相同 ID、不同內容一律拒絕。
- 網路中斷不能換新 ID 重送。
- 呼叫模型之前，先把請求存進資料庫並取得唯一執行權，避免同一件事被執行兩次。

### NFR-2 工作區寫入權

- 同一個工作區（或重疊的路徑範圍）同時只允許一個成員寫入。
- 回合正常結束、或使用者中斷且確認程序已停止，才釋放寫入權。
- 失敗且無法確認程序是否停止時，寫入權標為未知，持續擋住同一範圍，直到擁有者確認後手動解除。
- 若能證明程序已全部結束、且工作區內容與開始前相同，可以直接釋放。

### NFR-3 安全

- 預設只接受本機連線（127.0.0.1）。開放到其他網路必須由擁有者明確設定。
- 網頁首次使用要配對（例如輸入一次性配對碼），之後用 Cookie；所有會改變狀態的請求都要防 CSRF，並限制大小與頻率。細節如下：
  - 配對碼：擁有者在本機終端執行指令產生，伺服器有沒有在跑都可以；伺服器自己的輸出與 log 不出現配對碼。配對碼 8 個字元，不用 0、O、1、I 這類容易看錯的字元；10 分鐘內有效，只能用一次。輸錯 5 次，或產生了新的配對碼，舊的就作廢。資料庫只存雜湊。
  - Cookie：配對成功後發給瀏覽器一個隨機憑證，放在 HttpOnly、SameSite=Strict 的 Cookie 裡；資料庫只存雜湊。連續 30 天沒使用就失效，使用時自動續期。擁有者可以在瀏覽器登出（只撤銷這個瀏覽器），也可以在本機用指令撤銷所有已配對的瀏覽器。
  - 除了健康檢查、配對、查詢配對狀態與登出，所有請求都要帶有效的 Cookie，讀取與 SSE 也一樣，否則拒絕。讀取也要擋，因為對話內容屬於 NFR-4 的隱私資料。
  - CSRF：GET、HEAD 以外的請求都要帶自訂標頭；帶了 `Origin` 時必須和伺服器同源（含埠）；帶了 `Sec-Fetch-Site` 時必須是 `same-origin`。不能只靠 SameSite，因為 127.0.0.1 的不同埠算同一個網站。
  - Host：只接受 IP 位址或 `localhost`，加上設定的埠，用來擋 DNS rebinding；所以不能用主機名稱連線。
  - 大小：請求本體上限 512 KiB（524,288 位元組），任何 JSON 編碼方式下的最長訊息（FR-2 的 32,000 字）都放得下。
  - 頻率：改變狀態的請求合計每分鐘最多 60 次，其中送出私聊回合每分鐘最多 20 次；超過時拒絕，並告知幾秒後可以再試。讀取與 SSE 不限。內容不合格（例如欄位錯誤）的請求、同一個請求 ID 的重送都計入；因未配對、CSRF 檢查或超過頻率而被拒絕的不計入。
  - 以上檢查都固定開啟，不提供跳過配對或關閉檢查的開關。
  - 已知限制：Cookie 不分埠，本機其他埠的網頁伺服器也收得到這個 Cookie，這是瀏覽器的規則。開放到其他網路時走的是 HTTP，同一個網路的人可能看到 Cookie；開放前要另外處理 HTTPS，這不在 MVP 範圍。
- 成員在私聊與群聊中預設不使用工具；需要工具的功能（派工、實作）只在指定工作區內進行。
- AI 的回覆一律當成不受信任的文字顯示，不執行其中的指令、不把它當 HTML 渲染。

### NFR-4 憑證與隱私

- 憑證只存在擁有者本機（環境變數、各家 CLI 自己的登入），不寫進資料庫、log、錯誤訊息或 repo。
- 對話內容（擁有者的訊息、成員的回覆、群聊發言）只存在擁有者本機的狀態資料庫，除了送給該回合使用的 AI 服務，不送到其他地方；資料庫檔只有擁有者能讀寫。
- 預設不送出任何遙測資料。
- 程式不得寫死任何個人路徑、帳號或專案名稱；所有路徑都可由設定檔或環境變數指定。

### NFR-5 可移植與安裝

- 一般使用者照 README 的步驟，能在一台全新的 Linux 或 WSL 機器上裝起來。
- 每個轉接器各自獨立，沒裝某家 CLI 時，只有那個轉接器不可用，其他照常運作。

### NFR-6 可觀察性

- 每個回合記錄開始、結束時間、狀態與錯誤分類，不記錄提示詞全文或憑證。這裡的「記錄」指 log 與診斷檔；對話內容依 FR-2 存在狀態資料庫，不寫進 log 或診斷檔。
- 錯誤可以附一個診斷 ID，讓擁有者到本機的診斷檔查詳情；診斷檔要先遮罩可能的機密。

### NFR-7 擴充接口

- 本體要預留擴充接口：轉接器、顧問角色與範本、排程任務、介面面板這幾類，可以由另外安裝的擴充提供，不必修改本體的程式碼。
- 沒裝任何擴充時，本體照常運作。MVP 與 v0.2 的功能都屬於本體；更後面的功能哪些留在本體、哪些做成付費擴充，做到該功能前再決定，並寫回本規格。
- 擴充的程式碼不放在本 repo。
- 擴充只能透過公開、有文件的接口和本體往來，而且一樣受 NFR-2（寫入權）、NFR-3（安全）、NFR-4（憑證與隱私）約束，不能繞過。
- 分期：MVP 只要求不把這幾類寫死，例如成員與轉接器不能寫死成固定幾家。擴充怎麼安裝、怎麼載入，在做第一個功能型擴充前補進本規格。

#### MVP：轉接器登記處

- 本體只有一個地方登記「有哪些轉接器」。每個轉接器登記以下資料：
  - 代號（只能用小寫英文、數字與底線）與顯示名稱。
  - 回合請求可以帶哪些欄位。
  - 連到該轉接器的位置，例如本機 socket 路徑。可以由設定檔或環境變數覆寫，不能寫死個人路徑。
  - 支援哪些認證模式（見 FR-1）。
  - 給調度與主持人用的能力描述，以及模型等級對應。沒登記模型等級的轉接器，提示詞裡就不出現它的模型名稱。
  - 該轉接器特有的診斷規則（可選），例如錯誤分類方式。
- 下列行為一律從登記處取得轉接器清單與資料，不在各自的程式裡列出固定幾家：
  - 回合協定的請求驗證
  - 回合狀態的顯示名稱與連線位置
  - 調度現況快照
  - 調度提示詞裡的工作者清單與能力
  - 群聊的發言者、發言順序、顯示名稱與主持人候選順序
  - 診斷檔的錯誤分類
  - 成員設定可選的轉接器、各家支援的認證模式，以及能不能指定模型與推理強度（FR-1）
- 新增或移除一個轉接器，只需要改登記處（或之後的擴充），其他程式不必修改。
- 收到登記處沒有的轉接器代號時一律拒絕，不猜測、不改用別家。
- API key 模式與訂閱 CLI 模式是同一個轉接器的兩種認證方式，不另外登記成一家。
- 主持人候選與順序由擁有者設定。沒有設定時，依登記順序從已啟用的轉接器中選。
- 預設登記：Codex、Grok、Claude Code（見第 3 節分期）。
- 驗收：
  - 既有測試全部通過。測試裡寫死的轉接器名稱，可以改成從登記處讀，或改用測試專用的登記資料，但不能刪除或放寬斷言。
  - 另外要有測試證明：
    - 登記一個測試用的轉接器之後，回合驗證、調度快照、群聊順序都看得到它。
    - 移除一個轉接器之後，這些行為都看不到它。
    - 未登記的代號會被拒絕。

## 6. 不做的事

- 不做多使用者或雲端代管（SaaS）版本；MVP 只服務單一擁有者的本機。
- 不自動 commit、push、部署或付款。
- 不繞過任何 AI 服務的使用條款或額度限制。
